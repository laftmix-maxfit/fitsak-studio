# AGENTS.md — Fitsak Studio

Static site: HTML + CSS + vanilla JS, no build step. Hosted on GitHub Pages from `main`.
English is the root (`/`), Ukrainian is `/ua/`. Both must stay identical in content and structure. Pages: `/`, `/ua/`, `/sites/` and `/ua/sites/` (turnkey websites landing; the main offer is the free mockup: the brief form is built into `#mockup` right after the hero; its consultation form lives in the native `<dialog id="consult-dialog">`, and the contact block `#contact-fallback` holds the short inline contact form, which also is the no-JS path), `/privacy/`, `/ua/privacy/`.

## Rules

1. One task = one branch. Never work directly on `main`.
2. "Push" (або «пуш») only on the owner's explicit command. It means: merge the working branch into `main` and push `main`. Nothing else goes to `main`.
3. Cache busting: every CSS/JS reference has `?v=N`. Bump `N` in all pages when that file changes.
4. No `innerHTML`, `insertAdjacentHTML`, `eval`, `new Function`, `document.write`. Build DOM with `createElement` and `textContent`.
5. No secrets, tokens or personal data in the repo. `js/config.js` holds only public IDs and placeholders.
6. Mobile at 360–400 px is mandatory: one column, no horizontal scroll, contact button within reach.
7. Do not change `<title>`, meta tags, canonical, hreflang or sitemap unless the task is about SEO.
8. Honest report at the end of every task: what was verified, what was not, and the steps for the owner.

## Analytics

GA4 runs in **Consent Mode v2, advanced mode**: when `GA_MEASUREMENT_ID` is a real ID (not `G-XXXXXXXXXX`), `app.js` loads `gtag.js` on every page (script element created in JS, no gtag snippet in HTML). Order at start: `consent default` with `ad_storage`, `ad_user_data`, `ad_personalization`, `analytics_storage` = `denied` and `wait_for_update: 500`, `url_passthrough` on, then the stored choice (`localStorage` key `fs_consent`) is applied with `consent update` **before** `config`, so the first `page_view` already has the right state. Accept → `analytics_storage`, `ad_storage`, `ad_user_data` = `granted` (`ad_personalization` always stays `denied`); Reject → all `denied`. `track()` always sends events: while consent is denied Google receives cookieless pings without identifiers (`gcs=G100`), after Accept `gcs=G111`. `?internal=1` stores `fs_internal=1`; while it is set, `traffic_type: "internal"` is added to the GA config and to **every** event; `?internal=0` clears it. `?debug=1` stores `fs_debug=1` in sessionStorage and adds `debug_mode: true` to the GA config (DebugView). First-touch `utm_*` and `gclid` from the URL are kept in sessionStorage (`fs_utm_*`, `fs_gclid`, never overwritten) and sent with the forms.

Microsoft Clarity (`CLARITY_ID` in `js/config.js`, placeholder `CLARITY_ID` = off) is also loaded from `app.js` (`https://www.clarity.ms/tag/<id>`). `CLARITY_PRECONSENT: true` → the tag loads at once and gets `clarity('consentv2', {ad_Storage:"denied", analytics_Storage:"denied"})` (queued before the tag runs, so it stays cookieless) until Accept; `false` → the tag is not loaded before Accept at all. Accept → both `granted`; Reject → both `denied`. The switch is the owner's legal decision; `false` is the safest option for the EU. The privacy pages (EN and UA, Clarity section) say that sessions are recorded from the first page view, before the banner choice: if `CLARITY_PRECONSENT` becomes `false`, remove that sentence from both pages. Every `<form>` carries `data-clarity-mask="true"`, so typed values are never recorded; do not remove it.

The consent banner (`#consent`, all six pages) is compact, bottom on mobile and a card in the bottom-left corner from 720 px; Accept and Reject have the same style and size. While it is visible `body.has-consent` gets a bottom padding equal to the banner height (`--consent-h`, set by `app.js`) and the sticky button is hidden. The consultation dialog is in the top layer, so the banner never covers its submit button.

Every event is sent only if `typeof gtag === "function"`, inside try/catch, with no personal data, and always carries `page_language` (`en` or `ua`).

Package buttons (`data-package` with an `href="#id"`) pick the package in the form of the current page (`#audit` on the main pages, `#mockup` on /sites/: "I want a landing page" / "I want a website" set `landing` / `site` in the brief) and scroll to it. Buttons with `data-open-consult` (+ `data-package`, `href="#contact-fallback"`) open the consultation dialog instead: package preselected, focus on the name field, page scroll locked (`body.is-dialog-open`, sticky button hidden); closing (×, Esc, backdrop) returns focus to the opener and keeps typed data; after a sent request the form is reset on the next open. The main-page "Landing page + analytics" card links to `sites/` instead and only sends `service_click`. `?package=X` in an external link preselects the package once on load and scrolls to the form, only for forms placed on the page (the audit form, or the mockup brief on /sites/; not for the dialog and not for the short contact form). Package values are the same in every form: `audit`, `deep_audit`, `analytics`, `repair`, `landing`, `ads`, `site`, `support`, `consult`, `mockup` (the default of the mockup brief). Any `form[data-form-type]` is handled by the same code in `app.js` (`data-subject` = mail subject prefix; the consultation form also sends `business`); `data-form-type` is `audit`, `consult`, `contact_inline` or `mockup` and goes to analytics and to the lead email as `form_type` (an unknown value counts as `audit`). Sent leads go through Web3Forms (`WEB3FORMS_KEY`); no personal data is stored in the repo.

### Free mockup offer (/sites/, /ua/sites/)

The hero sells the free mockup: primary button "Get a free mockup" → `#mockup` (`data-cta="sites_hero_mockup"`), a small note under it and a plain text link "Or a free consultation" that opens the consultation dialog (`data-open-consult`, `data-cta="sites_hero_consult"`). The header button (`header_mockup`) and the mobile sticky button (`sticky_mockup`) also lead to `#mockup`; the pricing "Support → Discuss" and the case button still open the dialog.

`#mockup` (`data-section="mockup"`) comes right after the hero and holds the brief, built into the page (not a dialog): `<form id="mockup-form" data-form-type="mockup" data-subject="бриф на макет">`, ids prefixed `m-`. Required, in this order: `business_name`, `links` (website, Instagram or Google Maps: any text of 5+ characters, no URL check), `offer` (textarea, `maxlength="500"`), `contact` (`contactRule()`). Optional radio groups with no default choice (`.choice`): `site_goal` (`leads`, `calls`, `sales`), `launch` (`this_month`, `1_3_months`, `browsing`), `budget` (`lt5k`, `5k_15k`, `gt15k`; the labels are in UAH on the UA page and in USD on the EN page). Hidden `package` = `mockup`. The lead email gets every field plus `lead_id`, `source`, `gclid`, `page_language`, `form_type` = `mockup`; an unpicked radio group is sent as an empty string (`none` in analytics). The success text has no request number. Under the form: the "What happens next" steps and the promo line (keep its price and date in sync with the pricing badge). The NONA phone screenshot next to the form is shown from 960 px only, so on a phone the brief starts right under the heading.

### Contact block

`#contact` on the main pages, `#contact-fallback` on /sites/ and /ua/sites/; heading "Contact me directly" / «Напишіть мені напряму». One primary button: Telegram (`data-telegram-link data-messenger="telegram"`, static `https://t.me/studiofits` href, `target="_blank" rel="noopener"`). There is no Email (mailto) button and no Viber: the email is shown as text with a Copy button (`.email-row.js-only`, `data-copy-email`). Fiverr: only a small text link at the bottom of the block on the main pages (`.contact__note`), nothing on /sites/. Only /sites/ and /ua/sites/ have the short inline form under the button (`#contact-form`, `data-form-type="contact_inline"`, ids prefixed `k-`): `name`*, `contact`*, hidden `package` = `consult`, submit "Send". The main pages have no inline form because the audit form sits right above. The mobile sticky button hides while `#audit`, `#mockup`, `#contact` or `#contact-fallback` is on screen (and while the consent banner is shown).

### Form fields

Audit form (main pages): visible `name`*, `website`*, `contact`*; `message` sits in `<details class="form-more">` ("Add a comment (optional)"). Consultation form (/sites/ dialog): visible `name`*, `contact`*, `website` (optional, format checked when filled); `business` and `message` sit in `<details class="form-more">` ("Add details (optional)"). The package is `<input type="hidden" name="package">` (default `audit` on the main pages, `consult` in the consultation form and in the short contact form); package buttons and `?package=X` set its value, an unknown value keeps the default. There is no consent checkbox: a small notice with a link to the privacy page sits under the submit button. `app.js` validates only the visible required fields (plus the website format when it is filled); fields inside `<details>` only have `maxlength`, and an error inside a closed `<details>` opens it before the focus moves there. There is no "preferred way to talk" field any more. The short contact form (/sites/, `#contact-fallback`) has only `name`* and `contact`*, with the same validation. The `contact` field accepts anything a person can be reached by (`contactRule()` in `app.js`): an email, a Telegram `@name` / `t.me/name` / bare username, a phone (9–15 digits, spaces, brackets, hyphens, dots, `+` and the words viber/telegram/tel ignored), or any other text of 5+ characters; only an empty value or one shorter than 5 characters is rejected. In HTML the field has just `required` and `minlength="5"`, no `pattern`.

### Forms without JavaScript

Every `<form>` has `method="post"`, `action="https://api.web3forms.com/submit"`, `accept-charset="UTF-8"` and static hidden fields `access_key`, `subject` (ends with `(no-JS)`), `from_name`, `redirect` (`<base>/<this page>/?sent=1` on the main pages; on /sites/ each form has its own: `?sent=mockup`, `?sent=contact_inline`, `?sent=consult`), so a submit before or without `app.js` is delivered natively instead of going to the URL as a GET. `app.js` still calls `preventDefault()` and sends its own explicit JSON payload: fixed keys plus the visible fields and radio groups of that form by their `name` (hidden inputs are not read or validated). On `?sent=1` (the first form of the page) or `?sent=<form type>` it hides that form, shows its success text without a request number (the consultation dialog opens for `?sent=consult`) and removes `sent` from the URL; no `generate_lead` is sent for it. Checked on 2026-11-10: with the current Web3Forms plan the `redirect` field was ignored (the visitor lands on Web3Forms' own success page, `https://api.web3forms.com/submit/success`), so `?sent=1` only appears if that changes; the lead is still delivered and the URL carries no data. At the very start, before GA is initialised, `app.js` removes the whole query if it contains `name`, `contact`, `website`, `message` or `business`, so personal data never reaches `page_location`. The audit, consultation and mockup forms have a `<noscript>` note with the Telegram handle. On /sites/ and /ua/sites/ the consultation form lives in a `<dialog>` that cannot be opened without JS; the page buttons (`href="#contact-fallback"`) then jump to the contact block, where the short contact form is a normal form on the page and works natively (`required`, `minlength`), as does the mockup brief in `#mockup`. There is no `<noscript>` copy of the consultation form any more: without JS the page shows two forms, the brief and the short contact form. The Telegram button of the contact block has a static `https://t.me/studiofits` href (JS sets the same value from `js/config.js`): if the handle changes, change it in `js/config.js`, the contact-block buttons of the 4 pages and the `<noscript>` notes together. Email controls carry `.js-only` and are hidden without JS (`<noscript><style>` in the head).
